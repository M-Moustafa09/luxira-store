01

Auth foundation

Scope — Large New: RefreshToken entity, login/register UI Pure engineering — no sign-off needed

Every other deferred piece — Admin gating, Account, the authorization pass across existing controllers, rate limiting on /auth/* — sits on top of real identity existing. This has to go first.

Ships

  • Register / login / refresh / logout endpoints, BCrypt password hashing
  • Short-lived JWT access tokens + hashed, rotating refresh tokens
  • Swap ICurrentUserService to read real claims — the one seam it was built for
  • Guest → account cart & wishlist merge on first login
  • Rate limiting on /auth/*
  • Frontend: register/login screens, session handling

Judgment call, not a blocker

Guest-cart-merge behavior (auto-merge on login vs. asking first) — I'll default to auto-merge unless you want it to prompt.

02

Account module

Scope — Medium Depends on Phase 1 Pure engineering — no sign-off needed

This is Module 8 from the original plan, deferred only because it needs real accounts to mean anything. Natural continuation immediately after Auth while that context is still warm.

Ships

  • Profile view/edit
  • Real, reusable Address book (Checkout currently only snapshots a one-off address per order)
  • Order history list, backed by the Orders module already built
03

Admin API

Scope — Large Depends on Phase 1 (roles) Pure engineering — no sign-off needed

The single biggest unblocker for actually operating the store — right now every product, coupon, and order status change requires editing DbSeeder.cs and re-migrating. Needs Phase 1's role/claims model to gate it properly, which is also why it wasn't started earlier alongside the storefront.

Ships

  • Full CRUD: Products, Categories, Bundles, Coupons, Testimonials
  • Order management — status transitions, the piece Track Order has been waiting on since Module 6
  • Admin role + [Authorize] pass across every existing controller, not just new ones

Worth a check-in, not a hard block

Endpoint shape should track whatever the admin dashboard team is actually building against — a quick sync before this phase starts is cheap insurance.

04

Payment gateway

Scope — Medium–Large, depends on SDK Order infra already exists Blocked on gateway choice

Order creation and the Cash/Card split already exist from Module 6 — this phase is purely about making "Card" actually charge something. Can run in parallel with Phase 3 once the provider is picked; the interface itself doesn't need to wait.

Ships

  • IPaymentGateway interface — can be scaffolded immediately, independent of the decision
  • Real implementation once a provider is chosen
  • Wire into order creation; webhook/callback handling if the provider needs it

Hard blocker

Nothing here can be finished — not just started — until a gateway is chosen. Common Saudi-market options: Moyasar, HyperPay, Tap, PayTabs.

05

Security & compliance hardening

Scope — Medium Depends on Phases 1 & 3 Partly blocked — hosting + VAT

Sequenced once Auth and Admin exist, so there's a full surface to actually harden — locking down CORS before Admin exists just means re-doing it. Secrets strategy specifically needs to know where this is hosted.

Ships

  • Environment-driven CORS (no more hardcoded localhost:5173)
  • UseHsts() in production
  • Production secrets strategy (env vars vs. Key Vault, depending on host)
  • JWT hardening review
  • VAT calculation, if confirmed as required

Two open questions

Hosting platform — shapes exactly how secrets get managed.

VAT — are displayed prices already tax-inclusive (cosmetic only), or does real computation/reporting need to exist for compliance?

06

Performance pass

Scope — Small–Medium Highest leverage after Phase 3 Pure engineering — no sign-off needed

Caching Categories/Bundles/Campaign and paginating the three list endpoints that still lack it matters far more once Admin lets the catalog grow past the current five-category, two-bundle seed data. No dependencies — could technically move earlier, but the payoff scales with catalog size.

Ships

  • In-memory/response caching for near-static reads (Categories, Bundles, active Campaign)
  • Pagination on Categories, Bundles, Testimonials endpoints
  • Revisit Product-variant projection if the catalog has grown substantially by then
07

Observability & deployment infrastructure

Scope — Large, mostly infra Stabilizes once app surface settles Blocked on hosting choice

Can't pick a logging sink, a CI/CD deploy target, or a migration strategy without knowing where this actually runs. Sequenced after the application surface is mostly stable (post Admin/Payment) so the pipeline isn't being rebuilt every week.

Ships

  • Persistent logging sink (file or cloud, depending on host)
  • Health check endpoints
  • appsettings.Production.json + environment-variable config
  • CI/CD pipeline — build, test, deploy
  • Defined production migration strategy (current dev-only auto-migrate-on-startup won't do)
  • Real image storage (blob/CDN) — the frontend public/ folder is a placeholder from Module 2

Hard blocker

Hosting platform. This is the one decision that gates the most downstream work in the whole plan — worth resolving early even if the phase itself runs late.

08

Test debt

Scope — Medium, ongoing No dependencies Pure engineering — no sign-off needed

Listed here as a catch-up phase for the seven modules already shipped, but it shouldn't wait — I'd rather stand up the xUnit project during Phase 1 and require tests on everything new from that point forward, so this phase is really just backfilling Modules 1–7.

Ships

  • xUnit test project, wired into the solution
  • Regression tests for the two real bugs caught by hand during manual testing — the Cart add-tracking bug and the ProblemDetails serialization bug
  • Coverage for Cart/Order/Coupon discount math specifically — the highest-risk logic so far
  • Going forward: tests become part of "done" for every new phase, not a separate line item
09

Frontend polish

Scope — Small–Medium Mostly independent Bundle-to-cart needs your call

Grouped last for narrative clarity, but loading/error states specifically have zero dependencies and are cheap — reasonable to pull forward and slot in whenever there's a gap between other phases rather than strictly waiting.

Ships

  • Loading/error/empty states everywhere except Track Order (currently the only page that shows them)
  • Bundle → Cart, once the design decision lands
  • Trending searches: move off the last remaining static mock list, or confirm it should stay admin-curated content
  • Remove known-dead components (ProductGallery, ProductInfo)
  • Deliberate responsive/device pass

Working process stays the same. One phase at a time, review after each, no jumping ahead — same cadence as the original eight modules. Nothing above has been started; this is the sequencing proposal for you to approve or reorder before we begin.
